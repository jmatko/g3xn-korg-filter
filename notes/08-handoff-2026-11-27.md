## Kernel bugs (fixed in source, NOT yet built or heard) **[REF]**

All three are in `effect/traveler.c` and the manifests; fixed in the repo copy.

1. **Guard collision (causes the silence).** stomphacks puts the init guard word
   at `state[state_bytes/4]`. With `state_bytes: 32` that is `state[8]`, but the
   kernel stores `fc_smooth` in `state[8]`, overwriting the guard after the first
   block. On a bad guard the kernel writes zeros to both outputs. `state[9]`
   (lfo phase) also lay past the allocation. Fix: `state_bytes: 48` in both
   manifests (guard moves to word 12).
2. **Cutoff mapping was not logarithmic.** The exp polynomial had wrong
   coefficients (50% knob gave about 1523 Hz, not 690 Hz). Replaced with
   `exp(u) = (exp(u/4))^4`, Taylor to v^6; within 0.1% of 60→8000 Hz except the
   very top (about 7919 Hz vs 7928).
3. Stale comments about the state layout corrected.

**[?]** I could not compile, so I have not confirmed the new code passes the
stomphacks build checks (no divide, no calls, register pressure). If the build
verifier complains, look at the new `ev`/`expu` block first.

## G3Xn file format: what a stock effect looks like **[REF]**

Derived by diffing two stock effects the user downloaded from the pedal
(`PDL_REV.ZD2`, `PDL_BITC.ZD2`) against our MS Plus-layout build. Same ELF family
in all three: TI C6000, shared object, only `ABS32` / `ABS_L16` / `ABS_H16`
relocations, `Dll_*` / `Fx_*` naming. The stock ELFs have more sections (31 vs
20) and keep their symtab; ours is stripped. Probably irrelevant (the MS Plus
loader is name-blind), but unverified for the G3Xn.

| Part | Stock G3Xn | MS Plus build (before conversion) |
|---|---|---|
| target (offset 12) | `0x07` (a few effects `0x05`) | `0x90` / `0x91` (greyed out in Effect Manager) |
| group byte (95) and id top byte (99) | `0x0b` = PEDAL; Filter is `0x02` | `0x02` |
| group name (111, 11 bytes) | `PEDAL` | `FILTER` |
| bytes 16..88 | non-zero at 16, 18, 24, 40, 88; identical in both stock files | all zero |
| version (89) | `1.40` / `1.50` | `1.00` |
| ICON | 182 B, a 23x30 1-bit **BMP** | 936 B raw MS Plus screen frame |
| INFO (20 B) | `00*4 | badge[3]="PDL" | group[9]="PEDAL" | float32 dsp` | zeros + float only |
| PRMJ/PRME | first parameter `"pedal":true` | all `false` |
| 16-byte trailer | non-zero | zero |

Group map for the G3Xn: 01 DYN, 02 FILTER, 03 DRIVE, 04 AMP, 05 CAB, 06 MOD,
07 SFX, 08 DELAY, 09 REVERB, 0b PEDAL, 1e RHYTHM, 1f LOOPER.

The stock list (`zoom-zt2/zoom_fx_AllZDL7/G3Xn/unzipped/list_sorted.txt`) gives
id, file, version, dsp%, a hash column, and target for all 162 effects.

**Not reproducible:** the 16-byte trailer matches no MD5 of any part of the file
(tried `[:-16]`, `[4:]`, `[8:]`, `[12:]`, `[16:]`, `[128:]`, DATA). The hash column
in `list_sorted.txt` is not the MD5 of the downloaded file either. We leave the
trailer zero. If the pedal ever rejects the file, suspect it first.

## Protocol facts, from the user's real G3Xn log

Reply bodies below are the SysEx with `F0 52 00 6E` and `F7` stripped, so
`body[0] = 0x60`. (`P.parseSysEx` does this.)

- **List:** `60 25 00 00 2A 00` then repeated `60 26 00 00 2A 00`. Entries are
  `60 04 25 ...` with the NUL-terminated name from `body[11]`. End of list is
  `60 03 7a 7f 7f 7f 0f`. Then send `60 27`. 237 files on the user's pedal. **[HW]**
- **Exists:** `60 25 00 00 <name\0>`. Existing file: `60 04 25 ...`. Missing file:
  `60 03 7a 7f 7f 7f 0f`. **[HW]**
- **Read:** open `60 20 02 <9x00> <name\0>` (reply `60 04 20 ...`), then loop:
  `60 05 00` (reply `60 03 00..`, ignorable), `60 22 14 2F 60 00 0C 00 04 00 00 00`,
  `60 05 00` → **data reply**:
  `60 04 22 01 00 | len_lo | len_hi | pack7 data | crc5`
  i.e. status `body[1]==04`, length `(body[6]<<7)|body[5]`, data from `body[7]`,
  packed length `n + ceil(n/7)`, CRC in the last 5 bytes (7-bit groups low first,
  stored XOR 0xFFFFFFFF, over the unpacked block). Blocks are 512 B. End of file:
  `60 04 22 00 00 04 00 <n>` then a reply with length 0 / status != 04. Close with
  `60 21 40 00 00 00 00`, then `60 09`. **[HW]**
- **Error code** `7a 7f 7f 7f 0f` = u35 `0xFFFFFFFA` = **-6**. It is an error code,
  not a size. **[HW]** (Its meaning for `create` is unknown.)
- **Write (what `verify.html` sends, MS Plus-style):** `60 24 <name\0>` →
  rejected with `60 03 7a 7f 7f 7f 0f`. **[HW]** The same packet is what
  mungewell's `file_upload` sends. The G3Xn needs something different or an extra
  step first. **Zoom Effect Manager can install effects**, so a working sequence
  exists.

### Corrections to earlier notes
- **Note 06** says `verify.html`'s read parser "matches" the reply layout. It did
  not: it indexed `body[4]`, `body[8..9]`, `body[10..]` (mungewell's indices,
  which include the stripped `52 00 6E`). On a real pedal this returned 0 bytes
  (the "FLST_SEQ too small (0 B)" and "refusing to save a truncated backup"
  errors). Fixed. The "degraded USB state" explanation was wrong.
- **Notes 06/07** read `60 03 7a 7f 7f 7f 0f` as a file size or "file exists". It
  is -6, "not found / cannot".
- **Note 06**'s claim that `fileExists()` is wrong on the G3Xn is not supported
  by the log: `60 04` for existing files and `60 03` for missing files works.
- **Notes 03/04** said the G3Xn target bit was unknown. It is `0x07`.
